# Failure signatures

*Drift: **C** (code-bound). Verified against commit `78de930`, 2026-10-04. Sources at the end.*

A run that ends, stalls or degrades leaves two kinds of trace: text on stdout, and numeric series in wandb. This page maps the mechanism to the trace, so a trace in hand can be read back to the mechanism. The machinery behind each event is elsewhere: the start paths and the sidecar in [checkpoints-and-resume](checkpoints-and-resume.md), the OOM and step-time guards in [compute-guards](compute-guards.md), the batch the cut moves in [batch-size](batch-size.md), the retired-key inventory and the invariant rules in [config-validation](config-validation.md), the stage engine in [stage-protocol-engine](stage-protocol-engine.md), the fire/rewind path and its bars in [learning-rate](learning-rate.md), and the submission side that reads a job's stdout in [cluster-operations](cluster-operations.md).

`train.py::Modeller.train` opens a `wandb.init` context and every initialisation step, including `init_gfn`, runs *inside* it; everything up to and including the constructor call in the module's `__main__` block runs outside it. A failure's position relative to that line decides whether a wandb run exists at all.

The mapping, mechanism to signature:

| a warm start whose restored weights give a non-finite gradient at step 0 | the non-finite-gradient print at step 0, then the no-rewind-target warning when `._rewind_checkpoint_path` returns no target, as it does when none of `last_ok`, `best`, `running` and `stage_start` exists yet under this run name: only the rate is cut, and `gradnorm/nonfinite_steps` is nonzero from the first report | `train.py::Modeller.monitor_losses`, `.fire_loss_spike`, `._rewind_checkpoint_path` |
| non-finite gradient | `"Non-finite gradient at {step}"` on every such step; `"non-finite gradient at {step} (streak N) -> rewind + peak cut"` when a ten-step monitor call finds the consecutive streak at 1, 11, 21 | `train.py::Modeller.step_loss`, `.monitor_losses` |

## What the numeric series carry

Prints do not survive a run that is hard-killed: wandb uploads no console log for a run left in state `crashed`. The counters below ride the ten-step reporting clock into history and do survive, so several rows above are also readable as series after the fact.

The LR channel carries `lr_ctrl/scale`, `lr_ctrl/divergences` and `lr_ctrl/moderate_fires` among its keys (`controller.py::LRController._emit`). `divergences` increments in `on_divergence` alone, reached by both the bar path and the non-finite-gradient path; the `UNRECOVERABLE` branch raises before it, so an aborting run's final fatal event is not in the counter. `moderate_fires` counts the excursion tier separately.

The batch channel is `Batch Size` beside `batch/oom_events`, `batch/oom_ceiling` and `batch/ceiling_expiries` (`train.py::Modeller.ten_step_reporting`). `oom_events` counts every allocation failure including eval ones; `oom_ceiling` is set by a train-step OOM and never by an eval one, and reads 0 when no ceiling stands.

`gradnorm/nonfinite_steps` is the count of non-finite steps since the previous report and is reset on each report. MLIP crashes are counted in `energy/uma_crash_calls` and `energy/uma_crash_rows`. `uma_utils.drain_uma_phase_timing` returns both, including as zero, and resets them when a UMA crystal call has returned since the previous drain, and returns nothing otherwise. `MolecularCrystal.drain_energy_timing` merges them into the report only when the same reporting window also counted a call to `energies/base_set.py::BaseSet.log_reward`; a window that lacks either carries neither key. The pooled eval dict carries `nonfinite_rows` and `nonfinite_frac` on every eval, including as zero.

## Stalls, which emit nothing by themselves

A stage whose exit term names a metric nothing writes, and which declares no `cfg:stage.max_steps`, never advances and prints no message. `protocol.py::StageProtocol._advance_term` holds a streak when `_write_step` returns no new stamp, neither advancing nor resetting it, so the visible state is `protocol/exit_streak_<tag>` pinned at 0. The companion age separates the two zeros: `protocol/exit_age_<tag>` is the step distance to the last write of that metric the term judged, so it climbs without bound once writes stop, oscillates at the metric's own cadence when a bar is not met, and reads `-1` while the term has judged no write in the current stage state, which the checkpoint carries across a resume.

A stage that declares `cfg:stage.max_steps` is bounded. Once it has run that many steps, `protocol.py::StageProtocol.tick` requests an eval and `.maybe_advance` calls `.advance` with the exit unmet, printing `"protocol: stage '...' FORCED EXIT at max_steps=N (M steps in stage) -- its exit condition was NOT met; exit streaks {...}"`. `protocol/max_steps_frac` is the fraction of the cap spent.

The step bar is a `trange(init_step, self.args.epochs + 1)` carrying no loss, metric or stage (`train.py::Modeller.train`). It advances once per host iteration whatever happened inside it: identically through a rewind, through a run whose gradients are all non-finite, and through a stage that never exits. Under `cfg:lr_control.mode` `bracket` the loop also consumes the iterator by the count `controller.py::LRController.tick` returns: the promoted trial's horizon on an iteration whose bracket promotes a winning candidate, and 0 on every other iteration. Under `fixed` that count is always 0. Every other line is event-driven, so between events a healthy run and a stalled one emit the same bar.

The occupancy series `gpu/util_recent` and `gpu/util_policy`, whose sensor is in [gpu-occupancy](gpu-occupancy.md), are means over `cfg:gpu_util_window_s` and `cfg:gpu_util_policy_window_s` of samples from a thread started before the energy function loads (`train.py::Modeller._start_gpu_util_thread`), so they include initialisation. The number a scheduler judges is an out-of-process one, wandb's `system.gpu.0.gpu` or an `nvidia-smi` sidecar, sampled on a wall clock that knows nothing about the loop. The scheduler-side reading is in [cluster-operations](cluster-operations.md).

## Could be tooling

The table is a manifest, and it drifts the moment a message is edited. An AST walk could collect every `print` and `raise` reachable from `Modeller.train`, keep each format string's literal prefix, and emit the first two columns mechanically: a message with no row here appears as a row with no prose, and a quoted phrase matching no literal fails. The reader's half is a log scanner that matches those prefixes against a job's stdout, places each hit on the step axis beside `Batch Size`, `lr_ctrl/divergences`, `gradnorm/nonfinite_steps` and `energy/uma_crash_rows`, and prints the terminal state and last step. The stalls are what a scanner adds most to, since they are defined by the absence of a line: an exit streak at 0 with an age exceeding a multiple of `cfg:eval_period`, a `gradnorm/nonfinite_steps` that is nonzero at every report, a last history row far behind the last checkpoint.
